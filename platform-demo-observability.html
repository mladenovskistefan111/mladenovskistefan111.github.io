01 — Context

A realistic target for the open-source stack

Most of my production observability work has been in Datadog and Splunk. I wanted hands-on time with the open-source counterpart — the Grafana LGTM stack plus Pyroscope — and for that I needed an application with enough moving parts to be worth observing: several services, several languages, a database, gRPC between services, and a real request path through a storefront.

Google's Online Boutique fits that, and it is Apache 2.0 licensed. The service split, the gRPC contracts and the overall behaviour follow the original. What I built around it is the observability stack, the instrumentation wiring, the delivery pipeline for each service, and a few changes to how the services themselves work (section 03). The project is not finished — section 06 lists what is missing.

What is mine and what is Google's

The storefront idea and the service architecture come from Online Boutique. The Grafana stack configuration, the per-service telemetry setup, the dashboards, the Postgres-backed catalog and the CI pipelines are my work. I'd rather say that plainly than have it read as an application I designed from scratch — Reflective is the project where I did that.

03 — What I changed

Beyond wiring up the telemetry

Postgres-backed product catalog
The upstream catalog is served from a JSON file. Here it lives in PostgreSQL, loaded through a pgx connection pool. A single query loads the whole catalog into memory, and the service only goes back to the database on a SIGUSR1 reload signal or when its cache is empty — so a request never costs a query.
Parallel fetching on the home page
Rather than calling downstream services one after another, the frontend's home handler now fetches currencies, products and the cart concurrently, and converts each product's price in its own goroutine.
One telemetry shape across five languages
Every service sets its own name as OTEL_SERVICE_NAME, exports traces to Alloy and, in nine of ten, pushes profiles to Pyroscope, using the SDK for its language. That consistency is what lets one dashboard layout and one set of Alloy rules cover Go, C#, TypeScript, Java and Python.
A pipeline per service
Every service repository carries its own CI workflow. The tools differ per language — golangci-lint, ruff, dotnet format, govulncheck, npm audit, pip-audit — but the stages and the gates are the same.

04 — The observability pipeline

How the four signals flow

Traces. Services export OTLP to Alloy, which forwards to Tempo. Tempo's metrics generator turns the spans into service-graph and span metrics and writes them to Mimir, so the service map and the request-rate and latency panels are built from the traces rather than from separate instrumentation.

Metrics. Alloy scrapes the Prometheus endpoint every service exposes and also receives OTLP metrics, converting them to Prometheus format on the way into Mimir.

Logs. Alloy discovers containers through the Docker socket, labels each stream with the container name as service_name, and ships it to Loki. Grafana's Tempo datasource is configured to jump from a span to the matching logs.

Profiles. Nine of the ten services push profiles to Pyroscope directly, through the SDK, without passing through Alloy.

A configuration trap

Configuring Tempo's metrics generator is not enough to get service graphs and span metrics. The processors also have to be enabled under the overrides section, otherwise the generator ring stays empty and nothing is produced — and nothing reports an error either. There is a comment in the Tempo config marking exactly that line.

The Trivy gate sits before publishing, so an image with a critical or high CVE never reaches Docker Hub, and every image that does is signed with an SBOM attached.

06 — Honest gaps

What this project is not, yet

Known gaps

  • It runs on Docker Compose, not Kubernetes. There is no GitOps and no deployment automation behind the pipelines; they stop at a signed image.
  • CI is started by hand in nine of ten repositories. The push triggers are commented out. Only product-catalog-service runs on push to main.
  • Test coverage after publishing is uneven. Seven services get a post-publish test stage; ad, recommendation and email do not. For payment, currency and shipping that stage is a single gRPC health check, and the frontend's "load test" sends 1,000 requests to its health endpoint — a regression gate, not a realistic load profile.
  • One service is not profiled. The C# cart service does not send profiles to Pyroscope.
  • A dead scrape target. Alloy is configured to scrape a PostgreSQL exporter, but the exporter is not in the Compose file and no dashboard uses it, so there is no database dashboard.
  • No alerting. There are dashboards but no alert rules and no SLOs, which is the part of observability I do day to day at work.
  • Demo-grade hardening. Grafana runs with anonymous admin access, the database credentials are throwaway, most stack images are on :latest, and some GitHub Actions are referenced by tag or branch rather than pinned to a commit.

07 — Reflection

What it was for

Reflective taught me to instrument one application from the inside. This project is the other direction: take a set of services I did not design, in languages I use less often, and make them observable and shippable in a uniform way. Most of the work was in the seams — making five languages emit the same kind of telemetry, and making one pipeline shape fit five build systems.

What comes next

Moving it onto Kubernetes with Helm and ArgoCD, so the signed images are actually deployed by the platform. After that, alert rules and SLOs on top of the dashboards, push-triggered pipelines, and linking Pyroscope profiles to Tempo traces.
