Bookshop — Local Kubernetes, Observability & CI/CD

The same bookshop application, deployed locally on Minikube — but this time with a monitoring stack, a proper ingress setup, GitOps via ArgoCD, and a Jenkins CI pipeline running in Docker to compare against GitHub Actions.

01 — Context

The same application, done properly

The EKS project got the application running on Kubernetes — but it had no observability, no real understanding of how the pieces fit together at the cluster level, and a frontend/backend networking problem that was solved by brute force rather than by understanding. This project was the deliberate response to all of that.

The goal wasn't to build something new. It was to take the same bookshop application — the same Spring Boot backend, the same React frontend — deploy it locally on Minikube, and this time instrument it properly. Prometheus scraping application and database metrics, Grafana for visualization, ArgoCD for GitOps-style CD, and Jenkins running in Docker to understand what CI looked like before GitHub Actions.

Local rather than cloud for a simple reason: no cost, no apply/destroy cycle, unlimited iteration. The constraint this time wasn't budget — it was a laptop running at 95% RAM with Minikube, Jenkins, and everything else competing for resources.

What this project was really about

Building the mental model. How does a metrics pipeline actually work — from application instrumentation to scrape target to time-series data to dashboard panel? How does ArgoCD watch a Git repo and reconcile the cluster state against it? How does Jenkins compare to GitHub Actions as a CI tool? These were the questions. The bookshop was just the vehicle.

03 — What improved

Genuine steps forward from the EKS project

Ingress done correctly
The two-LoadBalancer workaround from the EKS project is gone. All services are ClusterIP. A single Nginx Ingress Controller routes by hostname. The frontend reaches the backend via springboot.local/api — a publicly resolvable URL the browser can actually use.
Database seeding via Helm
The SQL dump is bundled inside the Helm chart as a ConfigMap, mounted at PostgreSQL's init directory. On first startup, the database seeds itself. No Bastion host, no SSH tunnel, no CI pipeline step to sequence carefully.
PostgreSQL as a StatefulSet
Correct resource type for a database — stable network identity, ordered startup, persistent volume claim. The EKS project used a managed RDS so this distinction didn't come up. Running it in-cluster made it visible.
Semantic versioning
GitHub Actions workflow reads the commit message, bumps the version tag (major/minor/patch), pushes the tag. Jenkins picks up the latest tag and builds the Docker image with it. No more :latest only — every build has a traceable version.
Grafana datasource provisioned automatically
The Prometheus datasource is defined in a ConfigMap and mounted into Grafana's provisioning directory. On startup, Grafana picks it up automatically — no manual datasource wiring through the UI.
Cross-namespace service communication
Prometheus in the monitoring namespace scrapes Spring Boot in app-dev using the full cluster DNS name. Same pattern for the PostgreSQL Exporter reaching the database. Understanding how Kubernetes DNS works across namespaces was new here.

04 — The observability pipeline

How metrics actually flow

The Spring Boot backend exposes metrics via the Actuator's /actuator/prometheus endpoint — JVM heap usage, HTTP request rates, response times, thread counts, and more, all in Prometheus exposition format out of the box. The PostgreSQL Exporter connects to the database and translates internal PostgreSQL statistics into the same format.

Prometheus scrapes both targets every 15 seconds and stores the time-series data locally. Grafana connects to Prometheus as a datasource and provides the query and visualization layer. Building dashboards manually in the Grafana UI — writing PromQL queries, choosing panel types, arranging layouts — was the primary way of learning what the data actually meant and how to ask useful questions of it.

The goal was the mental model, not the dashboards

The dashboards themselves weren't the point. Understanding the full chain — application exposes metrics, scraper collects them on a schedule, time-series database stores them, query language retrieves them, visualization renders them — was the point. This is the same pipeline that underpins every production observability stack, just running locally on one laptop.

05 — Jenkins vs GitHub Actions

The CI comparison

Running both CI systems side by side on the same codebase was one of the explicit goals of this project. The setup for Jenkins was: pull the official Docker image, run it locally on port 8081, install the Maven, Docker, and Pipeline plugins manually, expose port 8081 via Ngrok to get a public URL for GitHub's webhook, configure the webhook in the GitHub repo, write a Jenkinsfile. The setup for GitHub Actions was: create a YAML file in .github/workflows/.

Both worked. The conclusion after six weeks of using both was unambiguous: GitHub Actions is significantly easier to use for most CI tasks. The plugin ecosystem that made Jenkins powerful in its era is also its main liability — every capability requires finding, installing, and maintaining the right plugin, and the configuration UI has not aged well.

Where Jenkins still makes sense

Jenkins has a place in environments with complex, long-standing pipelines that predate GitHub Actions, or where the CI system needs to run in an air-gapped or self-hosted environment with no cloud dependency. For a fresh project in 2024 on GitHub, it's hard to justify the operational overhead. That said — understanding how Jenkins works, what plugins do, and why it was the industry standard for a decade is worth the time it took to run it.

06 — Reflection

What this project actually was

Six weeks of filling in gaps. The EKS project left specific open questions — no observability, no understanding of ingress, no GitOps, only GitHub Actions for CI. This project answered all of them, deliberately, using the same application as a consistent baseline so the infrastructure and tooling changes were the only variables.

The most valuable outcome wasn't any individual tool. It was understanding how a modern application platform hangs together: application code instrumented and exposing metrics, a scraper collecting them, a time-series database storing them, a visualization layer querying them, a GitOps tool reconciling declared state against actual cluster state, a CI pipeline building and tagging images that the cluster pulls. Each piece is simple in isolation. Understanding how they connect is what takes time.

What came next

The local project established the foundations. What followed was taking everything learned — Kubernetes, Helm, CI/CD, observability — into real production environments at Nextsense and then Billtrust, where the stakes, the scale, and the complexity were all significantly higher.
