01 — Context

The honest starting point

This was my first real AWS project. I had been learning cloud for about two months — working through documentation, courses, and homelab experiments — and I wanted something concrete to show. The goal wasn't a polished production system. It was to prove to myself that I could take cloud concepts off the page and build something that actually ran.

The constraints were real: no budget to speak of, no experience to fall back on, and no AI tooling good enough at the time to paper over the gaps. Everything took longer than it should have. Some things I got right without fully understanding why. Others I got wrong without realising it.

Why it's on this portfolio

Not because it's impressive infrastructure — it isn't. It's here because it's the beginning of the thread. The Nextsense Kubernetes platform and the Billtrust SRE work didn't come from nowhere. This project, with all its gaps, is where the foundations were laid. Leaving it out would make the story look cleaner than it was.

02 — What was built

The architecture

A modular Terraform project that provisioned a WordPress site on AWS across two Availability Zones. Traffic flows through an Application Load Balancer in public subnets to an Auto Scaling Group of EC2 instances in private app subnets, which connect to a MySQL RDS instance in a separate private DB subnet layer. EC2 bootstrapping via a userdata script handled Apache, PHP, and WordPress installation automatically on every instance launch.

03 — What held up

The things past-me got right

Module separation
Networking, compute, database, loadbalancing, and cloudwatch-alarms are cleanly separated with explicit input/output contracts. This was intentional — I wanted it to look like real Terraform, not a single-file script. It worked.
Secrets Manager for DB credentials
Database credentials never appear in the Terraform code or state file. Provisioned via the AWS console, fetched at runtime via jsondecode(). No hardcoded passwords anywhere in the repo.
Remote state with locking
S3 backend with DynamoDB state locking and encryption enabled. This is non-negotiable in any real environment, and getting it right from the first project was the right instinct.
Custom CloudWatch metrics
Disk and memory aren't surfaced by CloudWatch by default — the agent config in userdata publishes them to a custom namespace. The alarm module then queries that namespace correctly.
Security group scoping
ALB and app instances are on separate security groups. App instances only accept traffic from the ALB SG, not from the internet directly. DB instances only accept traffic from the app SG.
Multi-AZ RDS
Disabled during development runs to save time and cost — enabled on the final deployment. The DB subnet group spans both AZs, so the infrastructure supported it cleanly when switched on.

04 — What didn't

The gaps — seen clearly now

GapWhat it means in practiceWhat I'd do now
No HTTPSAll traffic between the user and the ALB is plaintext HTTP. Passwords, session cookies — all unencrypted in transit.ACM certificate on the ALB, HTTPS listener on :443, HTTP → HTTPS redirect, HSTS headers.
Single NAT GatewayBoth private app subnets route outbound traffic through one NAT Gateway in us-east-1a. If that AZ has issues, EC2 instances in us-east-1b lose internet access.One NAT Gateway per AZ, or use VPC endpoints for AWS services to reduce NAT dependency entirely.
ASG health check: EC2, not ELBThe ASG only replaces instances that are terminated or stopped at the hypervisor level. An instance where Apache has crashed but the VM is still running will never be replaced.Set health_check_type = "ELB" so the ALB health check drives replacement.
Open egress on app SGThe app security group allows all outbound traffic to any destination on any port. Any compromise of an instance gives full outbound network access.Restrict egress to port 3306 → DB SG, port 443 → AWS services.
No shared filesystemWordPress uploads are stored locally on each EC2 instance. The two ASG instances have diverging filesystems immediately after any upload. This is a split-brain problem.EFS mount shared across all instances, mounted at wp-content/uploads via userdata.
Secrets Manager provisioned via UIThe secret is not in code — if this infrastructure were torn down and rebuilt, the secret would need to be recreated manually before terraform apply would succeed.Provision the secret as an aws_secretsmanager_secret resource in Terraform, with value from a .tfvars file excluded from version control.

The one I'm most proud of catching — eventually

The shared filesystem gap is the most interesting one in retrospect. WordPress running across two instances with local storage isn't just slightly wrong — it's fundamentally broken for any site that accepts uploads. It worked fine for a static demo site with no real content, which is exactly why it never surfaced as a problem during this project. The absence of failure isn't the same as correctness.

05 — Reflection

What this project actually was

A proof of concept built by someone with two months of AWS experience, no budget, and a strong desire to learn by building something real. Measured against that — it succeeded. The infrastructure deployed, the site loaded, WordPress ran. The module structure was clean enough that adding a new module later (cloudwatch-alarms) slotted in without restructuring anything.

The most valuable thing this project taught me wasn't any specific AWS service. It was the discipline of thinking in modules from the start — separating concerns, making dependencies explicit through outputs, keeping variables configurable rather than hardcoded. That pattern scaled directly into the Terraform work at Nextsense, just at a very different level of complexity.

What came next

This project wasn't the finish line — it was the starting point. Directly after, I took what I'd learned and pushed further: containerizing applications, writing Helm charts, standing up an EKS cluster on AWS, and building CI/CD pipelines with GitHub Actions.
