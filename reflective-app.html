01 — Context

Why build your own application

Every project up to this point used someone else's code — the bookshop application was containerized, deployed, and operated, but never written. That created a specific blind spot: the infrastructure work was solid, but the developer's perspective was missing. What does it actually feel like to build a service? Where do the pain points come from? What does good instrumentation look like from inside the code, not just from a dashboard?

The answer was to build something from scratch. Not a tutorial clone — a real application with authentication, business logic, a proper database schema, tests, and observability wired through every layer. The goal tracker was the vehicle: simple enough to build quickly, complex enough to be interesting, with auth and goals as naturally separate bounded contexts that justified the microservice split.

The real goal

Understanding developers better. The infrastructure work on real projects requires communicating with development teams, understanding their deployment constraints, and debugging their applications under load. Building a full-stack application yourself — writing the code, the tests, the Dockerfiles, and the observability — changes what you see when you look at someone else's system.

03 — OpenTelemetry instrumentation

Signals from inside the code

Each service initialises the OpenTelemetry Node SDK at startup, before any application code runs. The SDK is configured with a resource that identifies the service by name, version, instance ID, and environment. Three exporters are wired: OTLP/HTTP for traces, OTLP/HTTP for metrics, and OTLP/HTTP for logs, all pointing at the collector.

Auto-instrumentation handles the boilerplate — Express routes, HTTP client calls, and Pino log records all generate spans and are correlated automatically. On top of that, each service defines its own domain-specific metrics: the auth service counts authentication attempts, successes, and failures with outcome attributes; the API gateway tracks request counts and durations per route.

auth-service/observability.ts — domain metrics and database spans // Domain counters — auth outcomes tracked with type + success attributes const authAttempts = meter.createCounter('auth_attempts_total'); const authSuccesses = meter.createCounter('auth_success_total'); const authFailures = meter.createCounter('auth_failures_total'); // Database operation wrapper — creates a span, records duration, handles errors export const withDatabase Span = async <T>( name: string, operation: () => Promise<T>, attributes?: Record<string, string | number | boolean> ): Promise<T> => { const span = tracer.startSpan(name, { kind: SpanKind.CLIENT, attributes: { 'db.system': 'postgresql', ...attributes }, }); try { const result = await operation(); span.setStatus({ code: SpanStatusCode.OK }); return result; } catch (error) { span.recordException(error as Error); span.setStatus({ code: SpanStatusCode.ERROR }); throw error; } finally { span.end(); } };

What this looks like in Jaeger

A single user request to create a goal produces a trace that starts at the API gateway, shows the JWT validation middleware as a child span, then the proxied HTTP call to the goal service, and finally the Prisma database operation as a CLIENT span with db.system=postgresql and duration attached. The full request lifecycle — across two services and a database — visible in a single waterfall view.

04 — Testing

Why the auth service has tests

The auth service is the only service with a test suite — unit tests covering utilities, middleware, models, and error handling; integration tests covering the full request lifecycle through the Express app. Writing tests was part of the goal of understanding how developers work.

Unit tests
JWT utilities, password hashing, error classes, catchAsync wrapper, validation schemas, logger — each tested in isolation. Fast, no database dependency.
Middleware tests
Auth middleware and error middleware tested with mocked request/response objects. Verifies that invalid tokens are rejected and errors are formatted consistently.
Integration tests
Full HTTP request lifecycle through the Express app — register, login, token refresh. Tests the entire stack from route to controller to service to database.

05 — What was left unfinished

Where it stopped

The Nextsense job came before the project was complete. What was working: all four services running via Docker Compose, the full observability pipeline — traces in Jaeger, metrics in Prometheus, Grafana dashboards — and the auth service test suite. What wasn't finished: the Helm charts exist but weren't fully tuned, there was no CI/CD pipeline wiring the tests to image builds, and Loki for log storage was planned but never added.

Honest assessment

This is the most technically ambitious of the learning projects — full-stack TypeScript, microservice boundaries, database-per-service, distributed tracing, domain metrics, integration tests. It's also the most incomplete. The foundation is solid and the observability work is real, but the CI/CD and Kubernetes deployment goals didn't land before the job started. Given the choice between finishing a personal project and giving full attention to a production environment at Nextsense, the right call was obvious.

06 — Reflection

What building the code actually changed

The most valuable outcome of this project wasn't the code — it was the shift in perspective. Writing a service from scratch, hitting a bug in middleware ordering, debugging a Prisma migration that ran in the wrong environment, trying to figure out why a span wasn't showing up in Jaeger — these are the problems developers deal with daily. Having worked through them personally changes how you read an application's telemetry, how you interpret a slow database span, and how you talk to a development team about what their service is actually doing.

OpenTelemetry instrumented from the inside looks different from OpenTelemetry configured from the outside. Writing the withDatabaseSpan wrapper, deciding which attributes to attach to which spans, figuring out why correlation IDs weren't propagating through the Pino logger — that's a different kind of understanding than deploying a pre-instrumented application and watching the dashboards.

What came next

The Nextsense job. Real production infrastructure, real clients. The observability work here fed directly into the Datadog APM and RUM work, where the same concepts — trace sampling, metric cardinality, log correlation — appeared at a significantly larger scale.
