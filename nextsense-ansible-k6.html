01 — Context

Starting from nothing

A national telecoms operator was launching a major version upgrade of their public web store, built on Nextsense's proprietary CMS. Their existing setup was two virtual machines, everything co-located, no reverse proxy, no HA, and a manual deployment process that took around 30 minutes per server. For the new version, they provisioned 14 servers across their datacenter: 4 web servers, 2 CMS servers, 2 file share servers, 3 Nginx proxies, and a 3-node MongoDB replica set.

I was brought in as the first hire specifically for this engagement. The brief was to own everything from the operating system configuration upward: consistency across all VMs, zero-downtime deployments, a blue-green promotion workflow for their CMS editorial team, and infrastructure reusable enough to be adapted for other clients. There were no existing playbooks, no internal runbooks, no prior Ansible usage at the company.

Constraint

All servers were completely air-gapped — our client's datacenter security policy prohibited internet access from the VMs. Every package, every dependency had to be carried in manually and installed offline via dpkg or local file copy. This affected every role I wrote.

02 — Architecture

Blue-green deployment platform

The infrastructure uses a blue-green model with two branches that alternate between PRODUCTION and STAGE roles. Public traffic flows through a VRRP-managed virtual IP to a pair of HA Nginx proxies, which route to whichever branch is currently live. CMS editors access the other branch via a dedicated internal proxy. A single make publish command swaps the roles, synchronizes the MongoDB databases and file shares, and exits maintenance mode — all orchestrated as a single multi-playbook workflow.

03 — Engineering challenges

The hard problems

Branch detection and cross-playbook variable propagation

Knowing which branch is PRODUCTION at runtime — without hardcoding it — was central to every deployment and publish operation. The solution reads the active Nginx symlink in /etc/nginx/sites-enabled/ on the proxy servers. Both proxy clusters are checked and asserted to be on opposite branches — if they match, the playbook fails immediately before touching anything.

Because the publish workflow spans multiple imported playbooks, branch variables had to survive across playbook boundaries. set_stats with aggregate: true was the mechanism — it writes variables to Ansible's stats artifact, which persists across imported playbook boundaries in a way that set_fact does not.

The publish race condition — and the fix

When the publish workflow entered maintenance mode on the CMS proxy, it removed the current Nginx symlink and created a new one pointing at the target branch. The problem: between the moment the old symlink was removed and the cache directory deletion completed, a request would slip through to the newly empty cache path, partially repopulate it, and the playbook would crash trying to delete a directory that was actively being written to.

The fix was to give each branch its own cache directory — web_cache01 and web_cache02 — and delete the one belonging to the branch being deactivated, not the active one. The race condition is eliminated because the deleted directory is never the one being served from.

Discovered in production

This bug only appeared under real traffic load — it never surfaced during initial testing when the site wasn't yet public. Diagnosing it required understanding the exact sequence of Nginx cache writes relative to the maintenance mode switchover.

The publish workflow — what make publish actually does

Step 01
Connectivity and permissions verification
Pings all servers. Verifies sudo rights on Linux, Administrator rights on Windows, IIS service availability, MongoDB connectivity, and write access to all file shares. Fails fast on any issue before touching the running system.
Step 02–04
Lock, branch detection, health checks
Creates lock files on all servers simultaneously. Reads active Nginx symlinks and asserts PROD and STAGE are on opposite branches. HTTP health check against all web servers. MongoDB replica set status verified — all members must be PRIMARY or SECONDARY.
Step 05
Enter maintenance mode
IIS stopped on CMS servers. CMS proxy symlink removed and replaced with maintenance page. Main proxy symlinks switched to the target branch — public traffic now hits the new PROD. Nginx cache for the old branch cleared. Pre-warm GET requests fired against key URLs on the new branch.
Step 06–07
Database and file share synchronization
PROD database backed up with mongodump. STAGE database dumped. PROD database dropped and restored from the STAGE dump. Application user permissions re-granted. Target share backed up as backup.zip. STAGE share directories robocopy'd to PROD with /MIR.
Step 08–09
Exit maintenance mode and lock release
IIS restarted on CMS servers. CMS proxy maintenance symlink removed and replaced with target branch config. Nginx reloaded. Lock files removed from all servers. Completion summary printed showing which branch is now PROD and which is STAGE.

Production usage

This workflow ran 3–5 times per business day once the system was live. The non-technical marketing CMS team ran it daily in production for the duration of the engagement.

After go-live

04 — Performance incident

The system was live. Then real traffic arrived.

The infrastructure automation was complete, the publish workflow was running daily, and the site had gone live on the new 14-server setup. Light early traffic was fine. When real production load arrived, the site degraded significantly under concurrent users.

What followed was three intensive days of debugging with the team: development lead, systems engineer, a software architect brought in specifically for the investigation, and me on infrastructure and the data layer. It was a classic multi-layer performance problem — several independent bottlenecks, each tolerable in isolation, compounding into something that couldn't survive real concurrent traffic.

Application-level bottlenecks
The software architect attached a tracer and identified several expensive operations repeating on every user request that were candidates for caching or restructuring.
Unindexed MongoDB queries
The MongoDB profiler surfaced several frequently-executed queries running as full collection scans. Under concurrent production sessions the effect compounded significantly.
No response caching
Frequently requested content was hitting the full application stack on every request. Implemented at the Nginx proxy layer independently of the application timeline.
System-level overhead
The systems engineer identified security scanning configuration on the Windows servers adding per-request overhead that was invisible during low-traffic testing.

05 — Load testing platform

Kubernetes-native load testing with k6-operator

While the team applied fixes, I needed a way to quantify the improvement quickly. I provisioned k6 across available lab machines via a shell script and ran distributed tests pointing at the same InfluxDB endpoint. It wasn't polished — but it produced the numbers needed: before the fixes, around 100 concurrent users caused measurable degradation; after, 600 concurrent users at 10 req/s held without issue.

That prototype made the value obvious — if distributed load testing was useful once under pressure, it was worth building properly. The production version was built on a local Kubernetes lab cluster: k6-operator, InfluxDB, and Grafana all running inside Kubernetes, with a Makefile interface that made distributed load testing a single command.

Makefile — complete interface # Install k6-operator, InfluxDB, and Grafana — all in-cluster, pre-configured make install # Run a distributed load test — file is required, everything else defaults to 1 make load file=webstore-prod.js pods=3 vus=200 duration=10 # Generates TestRun CRD → kubectl apply → streams pod logs live # All metrics appear in the pre-provisioned Grafana dashboard automatically

Result

The site was fast, the team was relieved, and we had the numbers to back it up. Infrastructure automation that disappears into the background and just works is the actual goal.
