01 — APM Observability Audit

Finding the signal in the noise

Shortly after joining, it became clear that our client's Datadog APM spend had grown significantly without a corresponding improvement in observability quality. The fleet was running at 100% trace sampling across the board — no sampling strategy, no differentiation between high-value and low-value services, no consideration for what the data was actually being used for. The result was a fleet of Datadog agents in LIMITED RESOURCE status, dropping traces under the volume they were expected to process, and creating monitoring blind spots at the exact moments they were most needed.

The audit started with a straightforward question: what are we actually ingesting, and does it justify the cost? Two weeks of analysis across billing data, service ingestion summaries, agent health metrics, and trace samples produced an answer that was difficult to argue with.

The indexing paradox

The clearest signal that something was wrong: of the total allotted indexed spans capacity, only 6.6% was being used. Datadog's indexing algorithms are designed to retain traces that are statistically significant, unusual, or represent errors. Using only 6.6% of indexing capacity meant that 93.4% of what was being ingested was so repetitive and low-value that even Datadog's own systems didn't consider it worth keeping. The infrastructure was being overwhelmed to collect data that was immediately discarded as noise.

02 — The ingestion problem

Three services, the majority of the noise

Investigation into the highest-volume services revealed that a small number of services were responsible for the overwhelming majority of ingestion. Each had been running at 100% sampling — a default that had never been revisited. The problem wasn't that these services were unimportant. It was that 100% sampling of routine, repetitive, high-frequency operations provides no observability benefit over intelligent sampling, and carries significant cost at every layer: Datadog ingestion charges, AWS egress fees for transmitting the data, and agent CPU and memory overhead processing it.

High-volume event processor — the worst offender

A high-throughput streaming worker responsible for synchronizing invoice and payment records between two internal systems was generating a disproportionate share of total ingestion. Each message it processed triggered 8–10 spans — database reads, HTTP calls, database writes, and downstream notifications — and it processed hundreds of messages per minute continuously. The trace data was so voluminous that Datadog's UI could only display 0.1% of spans. The operation pattern was almost entirely routine: fast, successful, repetitive. The success rate exceeded 99%.

The question the audit posed directly: does capturing a trace for every successful sync operation provide any observability value beyond what 5% sampling would provide? With 5% sampling and 100% error capture, over a million traces per month would still be available — sufficient to monitor performance trends, detect anomalies, and debug any failure. The recommendation was 5% sampling with 100% error capture, reducing ingestion on this service alone by approximately 95%.

External API gateway — a different problem

The external API gateway handling partner and customer traffic presented a more nuanced challenge. Unlike the streaming worker, this service handles actual business transactions — every request represents a real customer or partner interaction. Traditional fixed-rate sampling was inappropriate here because the traffic is mixed: high-frequency routine calls alongside low-frequency critical operations, expected business errors alongside genuine infrastructure failures.

The recommendation for this service was Datadog Adaptive Sampling rather than a fixed rate. Adaptive sampling automatically adjusts rates per endpoint and status code — prioritising rare patterns, unusual errors, and high-latency requests while reducing sampling of repetitive successful responses. This preserves full error visibility, maintains statistical diversity across all traffic patterns, and adapts automatically as traffic changes. Complementary application-level logging to Splunk meant that reducing APM sampling did not create audit gaps — the business-critical event trail existed independently of trace data.

Customer-facing payment portal

A PHP-based customer portal where end users view invoices and make payments was generating substantial trace volume from routine web interactions — page loads, session lookups, database reads — all succeeding, all repetitive, all generating nearly identical traces. The portal had comprehensive logging and analytics outside APM that covered the same ground. The recommendation was the same 5% sampling with 100% error capture pattern applied to the streaming worker.

Projected impact — top three services

Optimising these three services alone was projected to reduce total monthly ingestion by approximately 40TB — eliminating all ingestion overage charges and bringing the fleet comfortably within the included baseline. Combined with a right-sized host commitment, the total projected APM savings exceeded $40,000 annually, before accounting for proportional reductions in AWS egress costs for trace data leaving AWS infrastructure.

03 — Implementation

Getting the prerequisites in place

The sampling strategy required a prerequisite that wasn't in place: the ability to configure error sampling rates independently of trace sampling rates. This feature requires sufficiently modern tracing library versions — several services were running libraries two to three years out of date, predating the capability entirely. Getting the sampling changes into production therefore required coordinating tracing library upgrades with development teams across multiple services before any configuration changes could be applied.

In parallel, the Datadog Agents across the fleet needed to be upgraded and remote configuration needed to be enabled. Remote configuration allows sampling rates and other Agent configurations to be changed directly through the Datadog UI without requiring application redeployment — a critical capability for an SRE team without direct access to application code or infrastructure configuration. Once remote configuration was enabled, sampling strategies could be deployed and adjusted in real time through the Datadog portal, with immediate effect across the fleet.

The monitoring blind spots that existed precisely when they were most needed — during incidents — were eliminated. Less data, more reliable signal.

RUM Audit

04 — RUM Observability Audit

The same problem on the frontend

RUM — Real User Monitoring — captures what actually happens when users interact with web applications in production: page load performance, JavaScript errors, network failures, user journeys. Unlike APM which instruments the backend, RUM instruments the browser. Our client, a payments company, the frontend is where customers experience the product directly — hosted payment pages, customer portals, partner integrations. RUM is how the team sees what customers see.

The same pattern found in APM appeared in RUM: 100% session sampling across all applications, persistent monthly overages above the committed session allocation, and no differentiation between applications where comprehensive monitoring was clearly justified and applications where it was clearly wasteful.

The RUM sampling constraint

RUM sampling has an important characteristic that APM does not: it is absolute at the session level. If a session is sampled out at initialization, no data is captured for that session at all — not page views, not interactions, and critically, not errors. This means RUM sampling decisions require more careful analysis than APM sampling decisions. Reducing RUM sampling on an application where errors are business-critical eliminates error visibility entirely, not just reduces it statistically.

This constraint shaped the entire optimization strategy: applications needed to be assessed individually based on what the RUM data was actually being used for and whether errors elsewhere in the stack provided equivalent coverage.

The clear quick win

The most obvious candidate for optimization was an SSO authentication frontend — high session volume, average session duration of 3.1 seconds, no user journey to analyze beyond a login redirect. Users pass through this application in seconds and are immediately redirected to their destination. Each "session" is an authentication handshake, not a user experience. The application had already had Session Replay disabled on the same reasoning — the same logic applied to base RUM session capture. Authentication errors are captured by backend systems and by the destination applications users redirect to. RUM provided cost without proportional observability value.

Retention strategy — the SKU transition

During the RUM audit period, Datadog transitioned RUM from a sessions-based billing model to a new SKU structure separating RUM Measure (derives metrics from sessions), from RUM Investigate (indexes sessions). Applying retention strategies to this new model — defining which applications warranted full Investigate coverage versus lighter Measure coverage — was part of the optimization work, layering on top of the sampling changes to bring total RUM spend within committed allocation.

Combined outcome

APM and RUM optimizations together — sampling strategy implementation, agent fleet cleanup, right-sized commitment planning, and RUM retention strategy — identified and delivered over $150,000 in annual savings while maintaining 100% visibility into critical errors and system health across the production fleet.

Other work

05 — Automation & toil elimination

Turning manual work into platform features

Exchange Online mailbox lifecycle platform

Our client operates over 700 Exchange Online shared mailboxes used for client communication and operational workflows. The provisioning, maintenance, and deprovisioning of these mailboxes was handled manually — a significant and recurring source of operational toil, and a risk: mailboxes approaching storage limits would cause service disruption for clients without proactive intervention.

The solution was a fully automated PowerShell platform covering the entire mailbox lifecycle. Provisioning is triggered by Jira ticket parsing — when a provisioning request arrives, the platform reads the ticket, creates the mailbox with the specified configuration, and updates the ticket with completion status. Daily retention policy enforcement runs across all 700+ mailboxes, identifying and applying size-based retention rules before any mailbox approaches its storage limit. Batch status reporting feeds into Datadog dashboards, giving the team real-time visibility into fleet health without manual checks. Deprovisioning follows the same Jira-driven pattern as provisioning — no manual intervention required at any stage of the lifecycle.

AI-assisted alert remediation with n8n

Recurring production incidents often follow the same pattern: an alert fires, an on-call engineer runs through a known runbook, confirms resolution, and closes the ticket. For common, well-understood incidents, this is pure toil — the decision tree is deterministic and the remediation steps are documented. The work in progress is an n8n workflow that intercepts these alerts, executes the relevant runbook steps automatically, verifies resolution, and logs the outcome. When automation resolves the incident, it closes the alert with a summary. When it cannot — because the failure is outside the expected pattern or remediation fails — it escalates to PagerDuty with a summary of what was attempted, giving the on-call engineer context before they pick up the page.

06 — Production operations

Day-to-day SRE

Beyond the project work, the role is production SRE in the fullest sense. The environment is spanning payment processing systems, invoice management platforms, and the integrations between them. On-call is 24/7 via PagerDuty, contributing to P1 incident response across multiple teams.

Production incidents range from payment processing anomalies and database performance degradation to Rundeck job failures, FTP connectivity issues, and synthetic monitoring alerts. Datadog is the primary observability platform — building and maintaining monitors, dashboards, and alerting pipelines, and using metrics, APM traces, RUM session data and logs from Splunk Cloud directly in incident investigation. The observability audit work wasn't separate from production operations; it came directly from operating the monitoring infrastructure and identifying where it was working against itself.
