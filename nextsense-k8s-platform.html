01 — Context

The problem this solved

Nextsense had just completed a large infrastructure migration — moving a 10-node Proxmox cluster (replacing Hyper-V, freeing up licensing costs) that hosted 100+ VMs across their datacenter. With that foundation in place, the business had a new requirement: their applications were being containerized, multiple clients needed isolated environments, and the team had no Kubernetes knowledge, no monitoring, and no repeatable way to provision clusters on demand.

I was brought in as the sole DevOps engineer responsible for designing, building, and delivering this platform from scratch. The brief was straightforward in scope but open in technical direction: deliver a production-grade Kubernetes solution on the existing Proxmox infrastructure that could be spun up repeatably, without manual steps, and handed off to a team that would need to operate it after I left.

Before building the production platform, I stood up an initial version of the cluster for Sobranie MK — a separate Nextsense client — which served as the proving ground for the architecture. The learnings from that deployment directly informed the design of the parameterized, reusable platform described here, and confirmed that the approach was sound before it was committed to production.

Ownership

This was a solo project. All architectural decisions, implementation, testing, and documentation were mine. I worked in regular consultation with the senior engineer who hired me — we discussed ideas, challenged each other's choices, and made some decisions together (notably the Velero backup strategy and the eventual migration to Cilium Gateway API). The code, the automation, and the operational runbooks are mine end to end.

02 — Architecture

What was built

The platform is a 3-control-plane, 3-worker Kubernetes cluster running on Talos Linux, provisioned entirely through code. A single terraform apply provisions the VMs, configures Talos, bootstraps the cluster, waits for stabilization, then hands off to Ansible which installs the full software stack — networking, storage, monitoring, backup — without any human intervention.

03 — Engineering challenges

The hard problems

Bootstrapping nodes with static IPs on an immutable OS

Talos Linux doesn't support cloud-init or traditional network pre-configuration — VMs must boot with DHCP and have configuration applied via the Talos API after boot. This created a bootstrapping problem: the Terraform infrastructure module provisions VMs which receive DHCP addresses, but the Talos module needs to apply machine configs with the desired static IPs — not the temporary DHCP ones.

The solution uses a two-stage data flow. The infrastructure module exposes the DHCP-assigned IPs as Terraform outputs. The Talos module receives both the actual DHCP addresses (for connecting to apply config) and the desired static IPs (to embed in the config). A single Talos machine config template is generated with PLACEHOLDER_IP strings, then string replacement is applied per-node at apply time.

modules/talos/main.tf — per-node config injection resource "talos_machine_configuration_apply" "controlplane" { count = length(var.actual_controlplane_ips) # connect via DHCP IP, but push config with static IP embedded node = var.actual_controlplane_ips[count.index] machine_configuration_input = replace( replace( data.talos_machine_configuration.controlplane.machine_configuration, "PLACEHOLDER_IP/${var.network_cidr}", "${var.desired_controlplane_ips[count.index]}/${var.network_cidr}" ), "PLACEHOLDER_IP", var.desired_controlplane_ips[count.index] ) }

The disaster recovery two-tier problem

The backup strategy required solving a chicken-and-egg problem: Velero restores Kubernetes resources, but Velero itself needs storage (Longhorn) and networking (Cilium) to function. A naïve full restore would try to bring up Prometheus, Grafana, ingress-nginx, and cert-manager before the storage layer was ready, causing cascading failures.

The solution is a dedicated disaster-recovery.yaml Ansible playbook that installs only the prerequisite layer — Cilium, Longhorn, CSI snapshot infrastructure, and Velero — and nothing else. Once Velero can see the MinIO backend and Longhorn can mount volumes, a single velero restore create command brings up the rest of the cluster.

Verified result

End-to-end recovery — from a destroyed cluster to all services operational with full historical data (Prometheus metrics, Grafana dashboards, Uptime Kuma monitors) — consistently completed in 18 minutes. RPO is 24 hours (daily backup at 3 AM). The Prometheus volume retained 414MB of historical metrics across the restore.

Ingress migration with zero downtime

Partway through the project, NGINX Ingress Controller announced its planned retirement. Rather than defer the migration, I performed a live migration of the running cluster from NGINX Ingress to Cilium Gateway API — reconfiguring traffic routing, updating all ingress resources, validating each service individually, and ensuring the LoadBalancer IP remained uninterrupted throughout. The automation was then updated so all future cluster provisioning would deploy Cilium Gateway API directly.

04 — Automation

From terraform apply to ready cluster

Phase 1 — ~5 min
VM provisioning
Terraform provisions 6 VMs on Proxmox (3 control plane, 3 worker) using the bpg/proxmox provider. VMs boot from the Talos ISO via CDROM. DHCP IPs are captured from Proxmox's QEMU guest agent output.
Phase 2 — ~5 min
Talos configuration and bootstrap
Machine secrets are generated. Per-node configs are applied to each VM via the Talos API using DHCP addresses, with static IPs injected via string replacement. The first control plane node bootstraps etcd. kubeconfig and talosconfig are written to disk.
Stabilization — 120s
Cluster stabilisation wait
A Terraform time_sleep resource ensures etcd quorum is established and the API server is stable before Ansible begins. This prevents race conditions where Helm tries to install before the cluster is ready.
Phase 3 — ~15 min
Platform stack installation
Ansible installs: Cilium (with kube-proxy replacement, Hubble, L2 announcements), cert-manager, Cilium Gateway API, Longhorn (with NFS backup target), kube-prometheus-stack, Uptime Kuma, CSI snapshot infrastructure, and Velero with automated daily backup schedule. All idempotent — safe to rerun.

05 — Validation

CNCF conformance testing

Once the cluster was operational, I ran the full Sonobuoy conformance suite in certified-conformance mode — the same mode used for official CNCF certification submissions. Sonobuoy was a new tool to me at the time, and I'll be honest: it crashed twice during initial runs due to misconfiguration before I understood its resource requirements and mode flags properly. The third run completed successfully after approximately two hours.

Result

400+ conformance tests passed. 0 failures. ~1000+ non-conformance tests skipped as expected. The cluster is fully CNCF-conformant on Kubernetes 1.34.1.

Running conformance testing wasn't a requirement — it was my own decision to validate the platform properly before handoff. If you're going to claim a cluster is production-ready, you should be able to prove it.

06 — Operational handoff

Built to be operated by others

Disaster recovery manual
Step-by-step runbook covering the full DR process, MinIO setup, NFS configuration, backup verification, and every failure mode encountered during testing. RTO and RPO clearly stated.
Upgrade manual
Zero-downtime Kubernetes version upgrade guide, including the VIP certificate issue, the dry-run step, per-node timing expectations, and a real timeline from the 1.33 → 1.34 upgrade.
Architecture decisions
Every major technical choice documented with rationale and alternatives considered — why Talos over Ubuntu, Cilium over Calico, Longhorn over Ceph, and what the trade-offs are.
Video walkthroughs
Recorded screencasts of: cluster provisioning, version upgrades, backup and restore, and key operational procedures. For whoever joins the team next.

Known limitations at handoff

The platform was delivered without GitOps (no ArgoCD/Flux), without log aggregation (no Loki), and with AlertManager deployed but notification channels unconfigured. These were documented explicitly in a KNOWN_ISSUES.md as planned next steps rather than hidden gaps.

07 — Reflection

What I'd do differently

Given more time, I would have replaced the NGINX Ingress → Cilium Gateway API migration with a direct-to-Gateway-API deployment from the start — the migration was successful but unnecessary complexity. I would also have set up external-dns earlier so ingress hostnames resolved automatically instead of requiring manual /etc/hosts entries.

The most valuable lesson from this project was operational: documentation and video walkthroughs are not a post-project afterthought — they're part of the deliverable. A platform no one else can operate isn't finished, regardless of how clean the code is.

The most technically interesting part was the Talos bootstrapping challenge. Working within the constraints of an immutable, SSH-free OS pushed me toward a cleaner infrastructure-as-code design than I would have naturally arrived at on a traditional Linux system. Constraints tend to do that.
